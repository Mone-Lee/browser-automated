# browser-test-draft

任何 Gherkin 起草工作都先按本流程做，再回到 `browser-test` skill 执行落盘与确认。

## 必做流程

1. 运行 `browser-test feature rules`，完整阅读输出。输出末尾的 `rulesVersion` 每次以当次输出为准，不得凭记忆或沿用旧值。
2. 逐条用例起草步骤，严格遵守规则输出中的拆分、断言、写操作与数据审查要求。需求资料先按 `browser-test` 的“需求与数据资料生成”整理为可追溯场景；已有用例保留原文，需求推导须保留规则依据，数据资料只补充前提与基准，不能替代验收规则。
3. 结果 JSON 顶层写入 `"rulesVersion"`；每条 case 写入 `dataReview: {required, basis, missing}`。
4. 通过 `--steps` 传入，或在 agent-request 中回复同样结构。
5. CLI 拒绝草案时，按报错逐条修正后重新提交，不要绕过校验，不要通过放宽措辞让校验通过。

## CLI 会拒绝的情况

- 缺少或过期的 `rulesVersion`。
- case 缺少有效 `dataReview`（`required` 为布尔值、`basis` 为非空单行、`missing` 为字符串数组）。
- 登录与进入页面、搜索、定位混写在同一个前提步骤里。
- 待确认问题（todo）笼统，例如“证据不足”“请确认”。

## 起草要点

输入生效方式不属于 Gherkin 生成阶段的确认范围：不推测或追问失焦、回车、等待等输入生效细节，不将其写入 todo 或 dataReview.missing，也不留下“按确认后的事件使输入生效”等占位表述。原文明示的操作可以保留；业务上的提交、确认和保存仍按原文处理。

- 前提按职责拆分：已登录、已进入页面、目标对象已定位分别写成独立 Given/And。
- 未指定特定账号、角色或权限时默认普通登录账号，保留登录前提，省略 role；不追问账号、凭据或访问权限，不写入 todo 或 dataReview.missing，不仅因普通登录设置 required: true。basis 可说明普通登录默认约定，但不声称已核验实际登录态。仅材料明确要求特定身份或权限时审查相关缺口；条件已明确且无需固定账号时，不索取具体账号。不继承其他 feature、复用地址来源或其他场景的权限要求；实际登录或访问受阻在执行阶段处理。
- 场景实际依赖但尚未提供的数据（明确要求的特定账号、业务库、SKU 集合、修改前值）不得补造；把影响场景的缺口写进 `missing`，并在相关步骤给出具体 todo，例如“请提供业务库名称、成功添加的 SKU 编码，以及用于核验的页面”。
- 集合断言区分“展示集合中没有不符合项”和“全部符合项均展示”，不得把“仅”擅自加强。
- 数值断言保留同一对象、字段、基准来源与取证顺序，缺口用 todo 提问。
- 写操作写在 When（或继承 When 的 And），对应结果写在 Then；仅打开设置或修改页面属于导航，不补写保存。
- 前置条件中的后台字段也必须在草稿阶段审查：前端冒烟边界覆盖 Given、When、Then 及其 And，不因后台字段位于 Given 或括号说明中就将其作为浏览器可核验条件。识别数据库字段状态、关联表记录、接口响应等后台条件时，区分测试数据准备依据与页面核验要求；不要仅凭字段名或状态枚举认定页面可以验证，也不禁止有明确页面依据的业务状态。
- 原文后台条件保留在结构化来源节点及 dataReview.basis 中，可在预览中用独立注释保留“数据准备依据，不由浏览器核验”；不得以括号形式混入最终可执行步骤。未确认映射时，在对应草稿步骤添加具体 todo：引用后台条件，说明浏览器无法直接核验，询问是否仅作为数据准备依据，以及执行时使用哪个商品标识、页面区域和可见状态核验；相关缺口写入 dataReview.missing。原文没有页面结果时，不凭业务常识补造。确认前不能把建议的页面步骤视为已确认或可执行。
- 用户已明确提供符合条件的商品标识时，将其记录为用户确认的数据准备依据，不重复索取后台证明；页面核验范围尚未确认时，只询问该范围。确认后，Given 仅描述已确认的对象和页面可观察的业务状态，后台条件留在来源或独立注释中；这不表示已验证数据库。忠实保留原文的要求不意味着必须把后台说明写入可执行步骤，未经确认不得静默删减或替换核验范围。
- 前端冒烟断言只验证页面可观察的文本、控件状态、列表和展示数值，不生成状态码、响应体、数据库或后台日志断言。原文只有后台预期时保留来源并具体询问对应页面结果，不擅自替换或删除。
- 每个 Then 只验证一个结果，多结果用 And 拆分；Then 及其 And 不执行点击、输入、提交等操作，原文要求的操作放在 When。断言写清页面/区域、对象/字段和期望文本、值或状态；禁用“正常显示”“处理成功”“页面正确”“符合预期”等模糊判据，已确认的“保存成功”提示文案可以精确引用。
- 起草前检查页面效果是否足够明确；缺少文案、字段或状态含义时，优先请调用方补充操作后的实际页面截图、对象及其认可的正确效果。同页面共用材料集中收集，不重复询问。需求或用户认可提供验收依据，当前截图不能自行证明正确性、持久化或全部分页结果；缺口在生成时提出具体 todo，不留给执行器猜测。
- 按当次 feature rules 中的好坏示例校准粒度；示例值仅作表达示范，不是真实测试数据。输出前逐条自检单一结果、操作归属、模糊词、页面取证边界及预期来源。
